# 12 · 角色展示、背包额度与储物门禁（2026-11-05）

旧的角色面板只显示血条和技能，背包是一张没有上限的扁平表，
门只是地图上的一个格子，储物箱和锁完全不存在。
本轮把这三件事做成**同一套可回放、可验证的规则**：
看得见自己有什么 → 知道还装不装得下 → 能开、能锁、能存、能取。

> 两条原则沿用全项目：
> **一、世界内核仍然是唯一事实来源**，前端只做展示与指令，不自己算额度；
> **二、引擎中立（蓝图第 11 条）**——锁只认凭证本身，不判定所有权、
> 不记录「这箱子是谁的」、不替居民决定该把钥匙给谁。NPC 自主用锁明确留待后续开发。

用户给的上锁设计预想是「输入、判断、开关功能相结合」，
所以这里没有写成散落的 `if (locked) return`，而是一条统一的三段管线。

---

## 一、背包：常规的三重额度

常规做法不是「最多装 N 个物品」，而是 **格子 + 堆叠 + 承重** 同时约束：

| 容器 | 格子 slots | 承重 maxWeight | 单类占格上限 perKindSlots |
|---|---|---|---|
| 居民背包 `BAG_RULES` | 24 | 80 | 6 |
| 储物箱 `CHEST_RULES` | 30 | 200 | 10 |

`ITEMS` 每项补上 `cat / stack / weight / emoji`：
`stack` 决定「这一堆占几格」（如木头 50 个一堆、炖菜 10 个一堆），
`weight` 决定总负重，`cat` 决定前端分组。

实现上刻意**不更换数据结构**：额度是 `bagUsage(inv, rules)` 从既有扁平
`inventory` 表算出来的视图，全世界二十多处 inventory 读写不必迁移。
所有「往包里加东西」的入口收敛到 `addItem()`：

```js
export function bagUsage(inv, rules = BAG_RULES) { /* → items / slots / weight / kinds / full */ }
export function bagFits(inv, delta, rules = BAG_RULES) { /* delta 允许负数 */ }
```

- `bagFits()` 支持**负数 delta**：先扣材料再产成品时，看的是净变化，不会把「越做越轻」误判为超重。
- 返回字段叫 `rule`（`slots` / `weight` / `unknown_item`）而不是 `reason`，
  避免覆盖动作自身的 `reason`；调用处统一 `{ ok:false, reason:"bag_full", ...fit }`。
- 产出动作 `craft / cook / chop / fish / forage / give / accept` 在装不下时**整笔拒绝，不吞材料、不吃冷却**。
- 世界义务场景（遗产继承、管理员发放、拍卖托管物归还）走 `addItemForced()`，
  不该因为收件人背包满了就凭空蒸发物品——这是刻意与玩家产出区分开的。
- `inventoryList()` 直接吐出 `emoji / catName / slots / weight`，角色页不再自己查表。

## 二、门与储物箱：一个 `props` 模型

`world.props` 是 `Map`，id 形如 `door:5,21` / `chest:34,38`。

| 来源 | 登记方式 |
|---|---|
| 地图上的门 | `ensureProps(world)` 扫描 `map.doors` 幂等登记 |
| 地图上的 `crate` 格 | 同一函数登记为 `chest`，`public: true` |
| 一张新地图连箱子都没有 | `ensureChest(world)` 在广场旁找一块草地补一口公共箱，否则存取链从第一天就是断的 |
| 居民自己 `build chest` | 落成 `crate` 格并同步 `makeProp()` |
| 旧存档 | `loadSave()` 后 `ensureProps()` 补登记，版本 1~4 都能读 |

`makeProp()` 的字段：`id / kind / x / y / label / open / lock{mode,locked,secret,hint} / public / createdTick / items`。
门与箱共用同一套开合、上锁、判断逻辑，只有两处物理差异：

1. 门开合要 `map.setDoor()` 同步 `walkable / opaque / soundproof`（视线、声音、寻路一起变）；
2. 只有箱子有 `items`，只有箱子能 `deposit / withdraw`。

**拆箱保护**：`actRemove()` 遇到箱内还有东西时返回 `chest_not_empty`，
先取空才让拆，避免一次性吞掉一串物品。

`publicProp()` 是对外唯一出口：给 `lock.mode / locked / hint / hasSecret` 和
`usage`（由 `bagUsage(items, CHEST_RULES)` 算出的箱内容量），
**从不输出 `secret`**，密码摘要和钥匙编号都不会经 SSE / `/api/props` 外泄。

## 三、「输入 → 判断 → 开关」三段管线

`src/props.mjs` 是唯一入口，所有操作都过 `propControl(world, cmd)`：

```
输入 input   → 解析凭证 / 物品 / 数量（缺什么就在这一段明确说出来）
判断 judge   → 校验凭证、额度、距离、开合状态（引擎只判断「对不对」，不判断「谁配不配」）
开关 switch  → 真正改状态（开门 / 上锁 / 存取），返回三段轨迹
```

| op | 行为 | 失败会落在哪一段 |
|---|---|---|
| `inspectProp` | 只读查看，不改状态 | — |
| `open` | 锁着时一步完成「输密码 → 判断 → 解锁 → 开」 | 输入（没给凭证）/ 判断（密码不对） |
| `close` | 关门/合盖，不受锁限制 | 本来就是关着的，直接成功 |
| `lock` | 上锁，要求已配好锁具 | 输入 / 判断（无锁具、已锁） |
| `unlock` | 只解锁，不推开 | 输入 / 判断 |
| `setLock` | 配置 `none / code / key`，改配必须交出旧凭证 | 输入（没设密码）/ 判断（旧凭证不对） |
| `deposit` / `withdraw` | 按居民身份存取，校验箱盖、锁、背包与箱额度 | 输入（物品名/数量）/ 判断（没开、没这么多、装不下） |

返回值永远带 `trace`，前端照着画步骤条：

```js
[
  { stage: "输入", ok: true,  detail: "密码已输入" },
  { stage: "判断", ok: false, detail: "密码不对" },
  { stage: "开关", ok: true,  detail: "门已打开" }
]
```

- **凭证**：`credential: {type,value}` / `code=` / `keyId=` / `credential="..."` 四种写法都收。
  密码锁存 `sha256(propId|secret)` 摘要（纯函数、跨机器一致），钥匙锁存编号；
  `setLock` 改配要验旧凭证，否则任何人路过就能换掉别人的锁。
- **距离**：带 `actorId` 时门 1.8 格、箱 2.2 格内才让操作；
  不带 `actorId` 是控制台语义（供观测站直接管理）。
- **`canAccess(prop, credential)`** 是给 NPC / 玩法层预留的**只读**查询，
  不碰状态，只回答「此刻能不能过这道锁」。

## 四、接入内核、存档与回放

| 位置 | 改动 |
|---|---|
| `world.mjs applyAction()` | 新增 `open / close / lock / unlock / setLock / deposit / withdraw / inspectProp` 八个动作，自动把 `actorId` 绑成发起居民；Agent 与控制台走完全相同的规则 |
| `actInteract()` | 门 / 箱改走 `propControl()`，灶台进食逻辑保留 |
| `pub(v)` | 增加 `inventory: inventoryList(v)` 与 `bag: bagUsage(...)` |
| `snapshot()` | 增加 `props: publicProps(this)` |
| `server.mjs` | 新增 `GET /api/props`、`POST /api/props/act`；capabilities 与 `CAPABILITY_LADDER` 财物层更新 |
| `persist.mjs` | `STATE_VERSION = 4`，存档包含 `lock.secret` 与 `chest.items`；但对外的 `publicProp()` 永不外泄 |
| `fingerprint.mjs` | 世界指纹纳入 props 的 `open / locked / mode / hasSecret / 箱内物品`，`secret` 只记 `0/1` 不记内容 |

**业务拒绝是正常结果，不是 HTTP 错误**：`/api/props/act` 恒返回 200，
成败由响应体 `ok` 表达（密码输错、背包满了都属于正常玩法反馈）。
否则浏览器会把每一次「密码不对」记成运行时错误，也会污染前端的错误统计。

## 五、角色展示页

`viewer/character.css` + `viewer/character-panel.js` 重做右侧 `#inspector`，三视图：

| 标签 | 内容 |
|---|---|
| 角色 | 姓名、职业、年龄阶段、心情、当前目标、需求三条 meter、技能；职业/阶段已中文化 |
| 背包 | 24 格网格 + 三条额度（格子 / 承重 / 单类占格）+ 物品分类、堆叠、单件重量 |
| 储物 / 门禁 | 附近或全部物件列表、开合、配置锁、上锁 / 解锁、存取；三段步骤条把失败点高亮在「输入 / 判断 / 开关」 |

数据源按量拉取：`GET /api/villagers/:id`（背包、技能、性格）、`GET /api/props`（门/箱状态）、
`POST /api/props/act`（执行）。权限口径有意区分：
开关和锁按控制台语义不带 `actorId`，存取必须带当前选中村民 id 且人在箱子 2.2 格内——
这正好对应「操作者是谁」在玩法上的差别。

新用户可达性上的几处细节：附近没有物件时列表回退到最近 8 个，不会一片空白；
详情区放在列表**上方**，点完箱子立刻能看到三段轨迹；
配置锁成功后收起表单并清空明文密码；地图上箱盖开合与锁扣有可见状态。

**一条完整操作路径**（不需要读文档也能走通）：
点地图上任一居民 → 点「角色」→ 切「储物 / 门禁」→ 选一口箱子 →
「设置锁」填密码 → 「上锁」→ 试着不给密码开门（卡在「输入」）→
输错密码（卡在「判断」）→ 输对密码一步解锁并打开 → 存取物品。

## 六、引擎中立边界与「待 NPC 开发」

用户明确把「上锁功能」标注为**待 NPC 开发**，所以本轮只把接口备好，不接管任何自主决策：

- 引擎不判定所有权、不发钥匙、不写「谁拥有这口箱子」；
- 不替居民决定给谁密码、要不要撬锁、什么时候锁门；
- `canAccess()`（只读）与 `propControl()`（动作）已公开，
  后续 NPC 侧可以在自己的目标/效用竞争里决定「要不要去开锁」，
  再把结果作为普通意图交给 `applyAction()`，与世界既有红线完全一致；
- 心境 / 记忆 / 性格漂移一概不碰，`minds.json` 与世界指纹行为不变。

## 八、变更影响范围

这一轮改动同时涉及内核与前端，涉及文件如下（clone 下来即为同一版本，无需手工合并）：

- 内核：`sim/src/{economy,props,world,map,persist,fingerprint}.mjs`、`sim/server.mjs`
- 观测端：`sim/viewer/{index.html,viewer.js,character.css,character-panel.js}`
- 验收：`sim/tools/{props-test,fuzz}.mjs` 与本文档

两点运行纪律：

1. **改了内核文件要重启 `sim/server.mjs`**，`STATE_VERSION` 才会升到 4；
   只换静态资源不重启，旧进程仍按 v3 存档格式写盘。
   旧档（版本 1~4）都能读，`loadSave()` 会自动 `ensureProps()` 补登记门与箱。
2. 浏览器端静态资源与湖北地图数据不受影响，启动器的四条最小接口契约不变。
